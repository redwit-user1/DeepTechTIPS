# 로컬 OCR 연구노트 데이터셋 활용 가이드

> 7GB 규모의 OCR 연구노트 데이터는 **이 프로젝트 최대의 공백을 채울 수 있는 자산**이다.
> 지금까지 확보한 데이터는 (a) 영어 실데이터 (b) 한국어 합성 데이터뿐이었다.
> 이 데이터는 **자연 한국어 R&D 실텍스트** — 우리가 못 가졌던 유일한 것이다.

## ⚠️ 먼저 확인할 것

연구노트는 **미공개 연구내용·개인정보·영업비밀**을 담는 법적 기록이다.
아래를 확인하기 전에는 학습·외부 전송을 하지 않는다.

1. **이용 권한** — 자사 데이터인가? 고객사 데이터라면 학습 이용에 동의가 있는가?
2. **개인정보** — 연구자·점검자 성명, 연락처가 포함되는가? (거의 확실히 포함)
3. **영업비밀** — 미공개 실험 조건·수율·조성이 포함되는가?
4. **반출 범위** — 원문을 사내 밖으로 내보낼 수 있는가?

> 본 저장소의 `data/` 는 gitignore 이며, 원문은 절대 커밋하지 않는다.

## 로컬에서 시작하기 (텍스트 데이터 기준)

**GPU·torch 불필요.** OCR 파이프라인 전체가 표준 라이브러리만 사용하므로
Python 3.9+ 만 있으면 노트북에서도 돈다(`pip install` 조차 필요 없다).

```bash
git clone <이 저장소> && cd DeepTechTIPS
git checkout claude/busy-wright-11w7w4

export GOONO_DEID_SALT='조직 고유 비밀값'     # 비식별화 salt (공개 금지)
bash scripts/run_local_ocr.sh /path/to/ocr    # 1~2단계 자동 (dry-run)
```

표본 결과를 확인한 뒤 전량 처리:
```bash
bash scripts/run_local_ocr.sh /path/to/ocr --write
```

산출물:
- `ocr_profile.json` — 구조·품질 통계. **원문 미포함이라 공유 가능**
- `data/real/labnote/notes.jsonl` — 비식별화된 구조화 레코드(gitignore 대상)

> 의존성이 필요한 것은 **학습 단계뿐**이다(`pip install -e ".[train]"`).
> 데이터 수확·무결성 검사는 그 전에 로컬에서 끝낼 수 있다.

### 이 세션에서 함께 작업하려면

7GB 는 관리형 개발 VM 에 올릴 수 없다. 두 선택지가 있다.

| 방법 | 설명 |
|---|---|
| **A. `claude --teleport`** | 이 세션을 로컬로 옮긴다. 대화 맥락이 유지된 채 **실데이터를 보며 파서를 함께 조정**할 수 있다. → `docs/H100_PLAN.md` |
| B. 결과만 공유 | 로컬에서 스크립트를 돌리고 `ocr_profile.json` 과 콘솔 출력(원문 없음)만 공유. 그에 맞춰 파서를 수정해 푸시 |

실데이터는 형식이 제각각이라 **파서 조정이 한두 번은 필요하다.**
A 가 반복 속도가 훨씬 빠르다.

## 3단계 파이프라인

### 1단계 — 프로파일링 (내용 노출 없음)

무엇이 들어 있는지부터 **원문을 보지 않고** 파악한다. 결과에는 원문이 포함되지 않아
그대로 공유해도 비교적 안전하다(그래도 눈으로 확인 후 공유할 것).

```bash
python scripts/profile_ocr_dataset.py /path/to/ocr
python scripts/profile_ocr_dataset.py /path/to/ocr --json profile.json
```

산출: 확장자 분포 · 한글 비율 · **연구노트 구조성 지수** · OCR 품질 신호 ·
**개인정보 위험(건수만)**.

이 결과가 다음을 가른다:
- 구조성 높음 + 한글 중심 → 곧바로 수확 가능
- 이미지만 존재 → **OCR 선행 필요**
- 개인정보 검출 → 비식별화 필수

### 2단계 — 비식별화 (`data/ocr/deidentify.py`)

**비가역 가명 치환**이다. 설계 원칙:

| 원칙 | 이유 |
|---|---|
| 비가역(해시) | 원본 복원 불가 |
| **구조 보존** — `연구자: 김민준` → `연구자: 연구자_A3F2` | 이름을 지우면 ALCOA+ `Attributable` 검사가 정상 노트를 '서명 누락'으로 오판한다 |
| 일관성 — 같은 이름 = 같은 가명 | 문서 간 동일인 추적이 되어야 `Consistent` 검사가 성립 |
| 감사 가능 | 무엇을 몇 건 치환했는지 보고(값은 남기지 않음) |

```bash
export GOONO_DEID_SALT='조직 고유 비밀값'    # 공개하지 말 것(재식별 시도 방지)
```

### 3단계 — 수확 (`data/ocr/harvest.py`)

```bash
# 기본은 dry-run — 무엇이 나올지만 보고
python -m compliance_gateway.data.ocr.harvest /path/to/ocr --limit 500
python -m compliance_gateway.data.ocr.harvest /path/to/ocr --write --out data/real/labnote
```

비식별화 → 파싱 → 기록 무결성 검사 → JSONL.

## OCR 노이즈 내성 (`data/ocr/parse.py`)

우리 가상 노트는 깨끗하지만 실제 OCR 은 다르다. 다음을 흡수한다.

| OCR 열화 | 대응 |
|---|---|
| 구획 제목 변형 (`4. 실험 결과` → `4 실험결과`) | 번호·공백 유연 매칭 |
| 콜론 변형 / 라벨 자간 (`연 구 자 `) | 구분자 집합 + 자간 허용 |
| 문장 중간 줄바꿈 삽입 | 문단 재결합 |
| 문자 혼동 (`2O24-O3-3O`) | 날짜 정규화 |
| 스캔 잡음 라인 | 짧은 잡음 제거 |

**개발 중 잡은 버그**: 문단 재결합이 `과제명:` 같은 **라벨 라인까지 이어붙여**
메타데이터 블록을 통째로 뭉갰다(필드 7개 중 5개가 오염, `실험 목적` 구획 소실).
→ 라벨 라인·구획 헤더는 결합 대상에서 제외. 수정 후 completeness 0.91 → **1.00**.

## 이 데이터로 할 수 있는 것 (가치 순)

### ① 기록 무결성 검사의 **실데이터 검증** — 최우선
현재 `integrity/` 는 가상 데이터에서 AUC 1.000 이지만, 그건 **규칙으로 만든 위반을
규칙으로 찾은 결과**라 KPI 근거가 못 된다. 실제 노트로 재측정하면 진짜 성능이 나온다.

> 주의: 실데이터에는 **정답 라벨이 없다.** 수확 결과는 "검사기가 무엇을 지적하는지"를
> 보여줄 뿐 정확도가 아니다. 정확도를 알려면 표본 200~300건을 사람이 검수해
> 정답을 만들어야 한다. 이것이 한국어 KPI 를 정직하게 주장할 수 있는 유일한 길이다.

### ② 한국어 R&D 문체 학습 데이터 (M2-3)
사업계획서의 "R&D Instruction 5만건" 목표에 직접 기여한다.
현재 우리 DPO 쌍은 200개 남짓이라 SLM 학습에 턱없이 부족하다.
7GB 라면 규모 문제가 해소된다.

### ③ OCR 오류 자체가 학습 신호
실제 ELN 은 스캔·수기가 섞인다. OCR 노이즈가 있는 텍스트에서도
ALCOA+ 판정을 하는 능력은 **GOONO 제품의 실전 요구사항**이다.

### ④ 도메인·기관 다양성
현재 가상 데이터는 3개 도메인 × 템플릿 4종이라 문체가 단조롭다.
실데이터는 연구자마다 문체가 달라 일반화 성능을 제대로 잴 수 있다.

## 규모 관리 (7GB)

- 이 개발 세션(관리형 VM)에서는 다룰 수 없다. **로컬 또는 H100 컨테이너**에서 실행한다.
- `--limit` 으로 표본부터 시작해 파이프라인을 검증한 뒤 전량 처리할 것.
- 텍스트만 7GB 라면 수억 자 규모다. 파싱 성공률·무결성 분포를 먼저 보고
  **어느 부분집합이 쓸 만한지** 판단하는 편이 낫다.
